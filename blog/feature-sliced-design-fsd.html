Feature-Sliced Design (FSD)

Feature-Sliced Design (FSD) 는 프론트엔드 애플리케이션의 규모가 커짐에 따라 발생하는 스파게티 코드와 복잡한 의존성 문제를 해결하기 위해 고안된 아키텍처 방법론입니다. 코드를 기능(Feature)과 도메인(Domain) 중심으로 분리하여 모듈화, 결합도 최소화, 응집도 극대화를 목표로 합니다.

FSD는 애플리케이션을 세 가지 주요 차원인 Layers(계층), Slices(슬라이스), Segments(세그먼트) 로 나눕니다.

1. 계층 (Layers)

최상위 디렉토리 구조를 구성하며, 애플리케이션의 비즈니스 로직과 기술적 책임을 수직적으로 나눕니다. 계층 간에는 엄격한 단방향 의존성 규칙이 존재합니다. (아래로 갈수록 더 추상화되고 재사용성이 높습니다.)

  1. app: 애플리케이션 진입점, 전역 스타일, 프로바이더(Providers), 라우터 설정 등 전체 앱의 초기화와 관련된 로직이 위치합니다.
  2. pages: 라우팅 단위가 되는 전체 페이지 컴포넌트입니다. 여러 기능(Features)과 위젯(Widgets)을 조합하여 화면을 구성합니다.
  3. widgets: 여러 슬라이스(Features, Entities)를 조합하여 만든 독립적이고 완성된 UI 블록입니다. (예: Header, UserProfileCard)
  4. features: 비즈니스 가치를 지니는 사용자 상호작용(Action) 단위입니다. (예: AddToCart, SendComment, AuthByEmail)
  5. entities: 비즈니스 도메인의 핵심 데이터 모델입니다. (예: User, Product, Order) 모델의 상태(Store)나 데이터를 가져오는 API 로직이 포함됩니다.
  6. shared: 특정 도메인이나 기능에 종속되지 않는 재사용 가능한 공통 코드입니다. (예: UI 키트, 유틸리티 함수, 공통 API 클라이언트)

💡 의존성 규칙 (Dependency Rule) 모든 모듈은 오직 자신보다 아래에 있는 계층(Layers)만 임포트(import)할 수 있습니다. 예를 들어, features는 entities와 shared를 가져다 쓸 수 있지만, widgets이나 pages를 임포트하면 아키텍처 규칙 위반이 됩니다.

2. 슬라이스 (Slices)

각 계층(shared와 app 제외) 내에서 특정 도메인이나 비즈니스 단위로 코드를 나누는 수평적 분할입니다. 슬라이스는 비즈니스 도메인을 기준으로 분리되므로 프로젝트마다 다릅니다.

  • 예: entities 계층 내에 user, product, article 이라는 슬라이스가 존재할 수 있습니다.
  • 격리 원칙: 동일한 계층 내에 있는 슬라이스끼리는 서로 직접적으로 임포트해서는 안 됩니다. (예: features/auth가 features/cart를 직접 참조 불가)

3. 세그먼트 (Segments)

슬라이스 내부를 기술적인 목적(Technical Purpose)에 따라 나누는 가장 작은 단위의 파일/폴더들입니다. 주로 다음과 같이 나뉩니다.

  • ui: UI 컴포넌트 (.tsx, .jsx, .css)
  • model: 비즈니스 로직, 상태 관리 (Redux slices, Zustand stores 등)
  • api: 서버와의 통신 로직
  • lib: 슬라이스 내부에서만 쓰이는 유틸리티 함수

디렉토리 구조 예시

src/
├── app/                  # 앱 초기화 및 전역 설정
├── pages/
│   ├── home/             # Home 페이지 슬라이스
│   └── profile/          # Profile 페이지 슬라이스
├── widgets/
│   └── header/           # 여러 Feature/Entity를 조합한 Header
├── features/
│   └── auth-by-email/    # 이메일 로그인 기능 슬라이스
│       ├── ui/           # 로그인 폼 UI 컴포넌트
│       ├── model/        # 로그인 상태 관리 로직
│       └── api/          # 로그인 API 호출 로직
├── entities/
│   └── user/             # 사용자 도메인 슬라이스
│       ├── ui/           # 사용자 아바타 등 기본 컴포넌트
│       └── model/        # 사용자 데이터 타입 및 스토어
└── shared/               # 공통 요소
    ├── ui/               # Button, Input 등 공통 UI 컴포넌트
    └── api/              # Axios 인스턴스 등

4. Public API (Index 파일)

FSD의 또 다른 중요한 특징은 모듈화의 캡슐화를 보장하기 위해 Public API(index.ts) 를 사용한다는 점입니다. 각 슬라이스는 자신의 디렉토리 루트에 index.ts를 두고, 외부 계층에서 사용해도 되는 컴포넌트, 타입, 함수만을 명시적으로 export 합니다. 외부 모듈은 반드시 이 index.ts를 통해서만 슬라이스 내부 요소에 접근해야 합니다.

5. FSD의 장단점

장점:

  • 확장성 & 유지보수성: 기능이 명확히 격리되어 있어, 프로젝트 규모가 커져도 특정 기능의 추가/수정이 다른 부분에 영향을 주지 않습니다.
  • 협업 용이성: 디렉토리 구조 자체가 아키텍처 문서 역할을 하므로 새로운 팀원이 구조를 파악하기 쉽습니다.
  • 리팩토링 안정성: 엄격한 단방향 의존성 덕분에 코드 변경 시 발생할 수 있는 사이드 이펙트를 최소화합니다.

단점:

  • 높은 초기 학습 곡선: 규칙이 엄격하고 생소한 용어(Layers, Slices 등)가 많아 팀 전체의 이해와 합의가 필요합니다.
  • 보일러플레이트: 작은 규모의 프로젝트에서는 불필요하게 많은 폴더와 index.ts 파일들이 생성되어 오버엔지니어링이 될 수 있습니다. (따라서 중대형 이상의 프로젝트에 적합합니다.)
