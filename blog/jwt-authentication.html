JSON Web Token (JWT) 기반 인증

JSON Web Token(JWT)은 당사자 간에 정보를 JSON 객체로 안전하게 전송하기 위한 간결하고 독립적인 방식을 정의하는 개방형 표준(RFC 7519)입니다. 현대 웹 애플리케이션과 RESTful API에서 가장 널리 사용되는 무상태(Stateless) 인증 방식입니다.

1. JWT의 구조

JWT는 점(.)을 구분자로 하여 세 가지 부분으로 구성된 문자열입니다. xxxxx.yyyyy.zzzzz 형태를 가지며 각각 Header, Payload, Signature를 의미합니다.

1.1. Header (헤더)

토큰의 타입과 해싱 알고리즘을 지정합니다.

{
  "alg": "HS256",
  "typ": "JWT"
}

이 JSON 객체는 Base64Url로 인코딩되어 JWT의 첫 번째 부분이 됩니다.

1.2. Payload (페이로드)

토큰에 담을 정보인 클레임(Claim)을 포함합니다. 클레임은 엔티티(주로 사용자)에 대한 진술 및 추가 데이터입니다.

  • Registered claims: iss(발행자), exp(만료 시간), sub(주제), aud(대상) 등 미리 정의된 클레임.
  • Public/Private claims: 사용자 정의 클레임. (예: 사용자 ID, 권한 등)
{
  "sub": "1234567890",
  "name": "John Doe",
  "role": "admin",
  "exp": 1516239022
}

이 정보 역시 Base64Url로 인코딩되어 두 번째 부분이 됩니다. (주의: Payload는 암호화되지 않으므로 민감한 정보를 담아서는 안 됩니다.)

1.3. Signature (서명)

토큰이 조작되지 않았음을 검증하기 위해 사용됩니다. 인코딩된 Header와 Payload를 점(.)으로 연결한 후, 서버만 알고 있는 비밀키(Secret Key) 를 사용하여 Header에 지정된 알고리즘(예: HMAC SHA256)으로 해싱하여 생성합니다.

HMACSHA256(
  base64UrlEncode(header) + "." +
  base64UrlEncode(payload),
  secret
)

2. Session 기반 인증 vs JWT 기반 인증

특징Session / Cookie 기반JWT (Token) 기반
상태 저장 (State)Stateful: 서버의 메모리나 DB(Redis 등)에 세션 정보를 저장Stateless: 서버는 토큰을 검증만 할 뿐 상태를 저장하지 않음
확장성 (Scalability)트래픽 증가로 서버 확장(Scale-out) 시 세션 공유(Session Clustering 등) 처리가 복잡함서버 확장이 매우 자유로움 (각 서버가 독립적으로 토큰 검증 가능)

토큰 통제력서버에서 즉각적으로 세션 무효화(강제 로그아웃) 가능이미 발급된 토큰을 만료 시간 전에 서버에서 임의로 폐기하기 어려움

3. JWT 보안 전략: Access Token과 Refresh Token

JWT는 상태를 저장하지 않으므로, 한 번 탈취되면 만료될 때까지 누구나 해당 사용자로 위장할 수 있습니다. 이를 방지하기 위해 토큰의 유효기간을 짧게 가져가는데, 이로 인해 사용자가 자주 로그인을 해야 하는 불편함이 발생합니다. 이를 해결하기 위한 표준적인 전략이 Access Token + Refresh Token 방식입니다.

  1. Access Token:
    • 리소스 접근에 사용되는 실제 토큰.
    • 유효기간을 매우 짧게(예: 15분~1시간) 설정하여 탈취되더라도 피해를 최소화합니다.
  2. Refresh Token:
    • Access Token을 재발급받기 위한 용도의 토큰.
    • 유효기간을 길게(예: 1주~1달) 설정합니다.
    • 주로 안전한 저장소(HTTP Only Cookie)에 저장되며, 서버 측 데이터베이스(또는 Redis)에도 저장되어 탈취가 의심될 경우 서버에서 해당 Refresh Token을 폐기(블랙리스트)할 수 있도록 통제권을 가집니다.

4. 클라이언트(Front-end) 토큰 저장 위치 비교

저장 위치장점단점권장 토큰
LocalStorage구현이 쉽고 접근이 용이XSS(크로스 사이트 스크립팅) 공격에 매우 취약 (JS로 접근 가능)Access Token (단기 유효 시 제한적 사용)
Cookie (httpOnly)JS에서 접근 불가하므로 XSS 공격 방어 가능CSRF 공격에 취약 (SameSite 속성으로 완화 필요)Refresh Token (장기 보관용)

가장 권장되는 보안 프랙티스: Refresh Token은 httpOnly, Secure, SameSite=Strict 속성을 부여한 쿠키에 저장하여 XSS와 CSRF를 동시에 방어하고, Access Token은 응답 바디(JSON)로 받아 프론트엔드의 메모리(예: 전역 상태 변수)에만 들고 있으면서 API 요청 시 Authorization 헤더(Bearer <token>)에 실어 보내는 방식이 가장 안전한 조합으로 평가받습니다.
