📝 2026-04-13 개발 기록

🔄 이전 작업 리뷰 [[2026-04-10-yolo26-test-and-custom-training|[2026-04-10]]]

  • [[2026-04-10-yolo26-test-and-custom-training]]
    • n-seg로 500 epoch학습시 놓치는 홀드수가 많음.
    • 모델 사이즈의 영향도 있으나, 데이터셋에 라벨링되지않은 홀드들, 특히 볼륨홀드같은경우에는 라벨링이 없어 이것이 문제가 될 가능성이 높아보임.
    • 이미지 내의 모든 홀드, 볼륨이 완벽하게 라벨링 되어있는 데이터셋 제작이 필요한것으로 보임.

🏗️ 진행한 작업 및 트러블슈팅

1. Segmentation 데이터 라벨링 기준 정립

  • 볼륨 홀드와 피스 홀드가 겹치는 경우의 라벨링 규칙 확립
    • YOLO(Instance Segmentation) 모델 학습을 위해, 볼륨 홀드 위에 작은 피스 홀드가 있을 경우 겹치게(Overlapping) 라벨링하는 것으로 결정.
    • 볼륨 홀드는 피스 홀드가 없다고 가정하고 전체 형태를 따라 마스크를 생성하며, 피스 홀드는 그 위에 독립적인 객체로 따로 마스크를 생성.
    • 이를 통해 모델이 볼륨 홀드의 전체적인 형태를 학습할 수 있도록 함.

2. AnyLabeling 툴 활용 및 데이터 포맷 변환

  • YOLO-seg는 images/, labels/ 폴더 구조와 폴리곤 좌표가 정규화된 .txt 파일 형식을 요구함.
  • AnyLabeling의 Export Dataset -> YOLOv8 Segmentation 기능을 사용하여 YOLO/COCO와 같은 포맷 선택가능.

3. 시스템 아키텍처 및 DB 스키마 설계 리팩토링

  • DB 스키마 분리 (Hold vs Pose): 기존 단일 InferenceResult 테이블을 생명주기와 데이터 포맷이 다른 HoldSegResult와 PoseKptResult 두 개의 테이블로 정규화(분리). 이를 통해 버전 관리와 포맷 관리(예: coco_17, body_25, yolo_polygon)의 유연성 확보.
  • Storage 아키텍처 설계 (Data Lake & Reference):
    • 사용자가 업로드한 원본 영상은 불변성을 유지하기 위해 Raw 버킷에 그대로 보존.
    • 썸네일, 배경 프레임, 추론 결과 JSON 등 AI 파이프라인에서 파생된 데이터들은 Inference/Asset 버킷의 구조화된 문제 ID 폴더 하위에 저장.
    • 파일 시스템 수준의 Symlink/Hardlink 대신 DB를 통해 두 스토리지 경로를 논리적으로 연결.
    • 파생 에셋(Asset) 버전 관리 및 데이터 리니지(Lineage) 추적: 배경 이미지 추출 방식(예: 단순 중간값 필터 vs AI 보정)에 따라 후속 모델(Hold Seg)의 성능이 달라질 수 있으므로, 썸네일과 배경 이미지 또한 버전 관리의 대상으로 포함. DB의 추론 결과 테이블에 source_image_path를 기록하여 어떤 에셋을 기반으로 추론되었는지 역추적 가능하도록 설계.
    • 스토리지/폴더 구조 (Problem ID 기준 논리적 분리): 
      /data_root/ (또는 s3://asset-bucket/)
└── problems/
    └── PRB-0001/                  # DB의 problem_id 와 매칭
        ├── assets/                # 파이프라인이 생성한 정적 에셋 (버전 관리 포함)
        │   ├── thumbnails/
        │   │   ├── v1.0_first_frame/thumb.jpg
        │   │   └── v2.0_best_shot/thumb.jpg
        │   └── backgrounds/
        │       ├── v1.0_median/bg.jpg            # 중간값 필터로 추출한 배경
        │       └── v1.1_ai_inpainting/bg.jpg     # AI 보정으로 사람을 지운 배경
        │
        └── inference/             # AI 모델이 생성한 추론 결과 (수치 데이터)
            ├── hold_seg/
            │   ├── v1.0_yolo/                    # v1.0_median 배경을 기반으로 추론
            │   │   └── seg_result.json
            │   └── v2.0_custom_seg/              # v1.1_ai_inpainting 배경을 기반으로 추론
            │       └── seg_result.json
            └── pose_kpt/
                ├── v1.0_coco17/
                │   └── pose_result.json
                └── v2.0_body25/
                    └── pose_result.json

※ 원본 영상(video.mp4)은 이 폴더에 복사하지 않고, DB(raw_video_url)를 통해 
   Data Lake(Raw 버킷)의 주소를 직접 참조하여 I/O 및 용량 최적화.

4. Background Extraction (배경 이미지 추출) 알고리즘 선정

  • 홀드 세그멘테이션의 입력으로 사용될 '사람이 가려지지 않은 깨끗한 벽면 이미지'를 얻기 위한 알고리즘 검토.
  • 후보군:
    1. Median Filter (중간값 필터): 여러 프레임의 픽셀별 중간값을 취해 움직이는 사람을 제거. 연산이 빠르고 단순하여 정적인 클라이밍 벽면에 매우 적합.
    2. MOG2 (Mixture of Gaussians): 가우시안 혼합 모델을 이용해 배경과 전경(사람)을 분리.
  • 결정: 빠른 파이프라인 구축을 위해 **1번(Median Filter) 방식을 우선 도입(v1.0)**하여 테스트 진행. 추후 에셋 버전 관리 아키텍처를 활용하여 2번 알고리즘 등 고도화된 방식을 순차적으로 적용 및 비교할 예정.

5. 파이프라인 오케스트레이션 및 분산 시스템 아키텍처

  • 영상 업로드부터 AI 추론까지의 전체 흐름을 제어할 시스템 아키텍처 논의.
  • 단순 Serverless나 단순 Airflow 중 택일하는 대신, 역할 분담형 마이크로서비스(MSA) 아키텍처 도입 결정. 특히, CPU/GPU 리소스의 효율적인 스케일링을 위해 Celery Worker(CPU)와 Triton Server(GPU)를 논리적/물리적으로 완전히 분리하는 아키텍처 채택.
    • Front-stage (가벼운 I/O): API Server & Lambda
      • 영상 S3 업로드 (Presigned URL) 처리 및 DB 상태 초기화, 메시지 큐(Redis/SQS)에 분석 작업 발행.
    • Back-stage (CPU Heavy Task): Celery Worker
      • 영상 다운로드, 프레임/썸네일 추출 작업 수행.
      • 딥러닝 프레임워크 없이 가볍게 구성되며, 추출된 이미지를 gRPC 통신을 통해 Triton Server로 전송. (네트워크 대역폭 최적화 및 직렬화 오버헤드 최소화)
    • Inference-stage (GPU Heavy Task): Triton Inference Server
      • 파이썬 코드 구현 없이 NVIDIA Triton 공식 도커 이미지를 사용하여 모델(YOLO, Pose) 서빙 전담.
  • 개발 및 배포 전략:
    • 로컬 개발 환경: docker-compose.yml을 사용하여 Redis, API Server, Celery Worker, Triton Server를 논리적으로 분리된 컨테이너로 띄워 개발.
    • 클라우드 배포 환경 (AWS 등): 역할을 분리한 코드베이스를 바탕으로, CPU 전용 인스턴스(Celery)와 GPU 전용 인스턴스(Triton)에 각각 나누어 배포. 이를 통해 트래픽 변화에 따른 독립적이고 비용 효율적인 Auto-Scaling 구현.

6. 파이프라인 병렬 처리 최적화 (Pipeline Parallelism)

  • 분석 파이프라인의 병목 구간을 식별하여 처리 속도 최적화 방안 도출.
  • 배경(썸네일) 추출이 완료된 시점부터는 입력 데이터가 분리되므로, **Hold Seg(배경 이미지 기반)**와 Pose Kpt(비디오 원본 기반) 추론 작업이 서로를 기다릴 필요 없이 병렬로 실행 가능함을 확인.
  • Kafka와 같은 무거운 스트리밍 플랫폼 도입 대신, **Celery의 Canvas 기능(group, chord)**을 활용하여 워크플로우를 구성하기로 결정.
    • group: Hold Seg와 Pose Kpt 작업을 Redis 큐에 동시에 던져 Triton 서버(GPU)에서 병렬 추론 유도.
    • chord: 두 병렬 작업이 모두 완료되었을 때만 후속 작업(상호작용 분석 및 DB 업데이트)이 실행되도록 콜백 로직 구현.
  • 이를 통해 전체 분석 소요 시간을 대폭 단축하고 GPU 리소스 활용률을 극대화할 예정.

💡 새롭게 알게 된 것 / 메모

  • Pose Estimation의 Keypoint 포맷은 다양함(COCO 17, OpenPose BODY_25 등). 발끝 추적이 중요한 클라이밍 분석에서는 향후 BODY_25 포맷 적용을 고려할 필요가 있음.
  • 대용량 미디어 데이터를 다룰 때는 원본 데이터(Raw)와 가공 데이터(Inference)를 철저히 분리하고 DB를 통해 참조하는 것이 클라우드 네이티브 환경 확장에 유리함.
