Claim Check Pattern 이란?

**Claim Check Pattern(클레임 체크 패턴)**은 메시지 기반 시스템이나 비동기 분산 아키텍처에서 대용량 페이로드(Payload)를 효율적으로 처리하기 위해 사용되는 디자인 패턴입니다. 공항이나 호텔의 수하물 보관소에 짐을 맡기고 '보관증(Claim Check)'을 받는 것과 똑같은 원리로 동작합니다.

메시지 큐나 데이터베이스에 크기가 큰 데이터를 직접 전달하거나 저장하는 대신, 실제 데이터는 외부 스토리지(예: AWS S3, Azure Blob Storage)에 저장하고 시스템 간에는 해당 데이터의 **참조값(Reference, 보관증)**만을 주고받는 방식입니다.

도입 배경: Climbing Cam 프로젝트의 후처리 데이터

Climbing Cam 프로젝트를 진행하면서 사용자가 업로드한 영상을 기반으로 Pose Estimation 등의 무거운 AI 후처리를 수행해야 했습니다. 초기에는 이 후처리된 결과 데이터를 어떻게 저장하고 시스템에 전달할지 두 가지 방안을 두고 고민했습니다.

  1. 모든 결과를 DB에 직접 저장

    • 장점: 관리가 단순하고 트랜잭션과 데이터의 일관성을 유지하기 쉽습니다.
    • 단점: Pose Estimation 결과 데이터의 크기가 상당히 큽니다(다량의 좌표 데이터 등). 이를 DB에 직접 다 때려 넣을 경우, DB 스토리지 비용이 급증할 뿐만 아니라, I/O 병목 현상 및 쿼리 조회 시 메모리 부족(OOM) 등의 심각한 성능 문제가 발생할 위험이 높았습니다.

  2. 모든 결과를 S3에 무조건 저장

    • 장점: 대용량 데이터를 저렴하고 안전하게 저장할 수 있습니다.
    • 단점: 상태 값이나 매우 작은 크기의 결과까지 모두 S3에 저장하게 되면, 불필요한 네트워크 I/O가 발생하고 로직이 파편화되어 데이터 관리의 복잡성이 커집니다.

이 두 가지 방식의 트레이드오프를 해결하고, 시스템의 성능과 확장성을 동시에 보장하면서도 일관성을 잃지 않기 위해 Claim Check Pattern을 도입하기로 결정했습니다.

아키텍처 구현 및 동작 방식

Climbing Cam 프로젝트에 적용된 패턴의 흐름은 다음과 같습니다.

  1. 저장 (Store): 영상 후처리 파이프라인(Worker)이 Pose Estimation 작업을 완료하면, 크기가 큰 결과 데이터(JSON 등)를 AWS S3에 업로드합니다.
  2. 보관증 발행 (Claim Check): S3 업로드가 완료되면 해당 파일의 Object Key나 접근 URL(보관증)을 반환받습니다.
  3. 참조 전달 (Pass Reference): 후처리 완료를 알리는 이벤트 메시지나 DB의 결과 레코드에는 실제 대용량 데이터 대신 이 **Object Key(보관증)**만을 포함시켜 저장합니다. 메인 DB는 가벼운 상태를 유지합니다.
  4. 데이터 조회 (Retrieve): 클라이언트나 다른 마이크로서비스에서 상세 결과 데이터가 필요할 때, DB에서 Object Key를 우선 조회한 후, 이를 이용해 S3에서 실제 대용량 데이터를 다운로드하여 사용합니다.

왜 이 패턴을 사용해야 하는가? (장점)

  • 성능 최적화 및 DB 부하 감소: RDBMS나 메시지 브로커가 대용량 데이터를 직접 처리하지 않으므로 부하가 크게 감소합니다. DB는 가벼운 메타데이터와 참조 링크만 관리하면 되어 쿼리 성능이 유지됩니다.
  • 메모리 보호: 애플리케이션이나 큐 워커가 거대한 메시지를 한 번에 메모리에 올리다가 발생하는 OOM(Out of Memory) 현상을 방지할 수 있습니다.
  • 비용 절감: 비싼 고성능 DB 스토리지 대신, 상대적으로 저렴한 S3와 같은 오브젝트 스토리지를 100% 활용할 수 있습니다.
  • 확장성 증가: 컴포넌트 간에 주고받는 페이로드(보관증)의 크기가 항상 작고 일정하게 유지되므로, 트래픽이 급증해도 안정적인 비동기 메시지 처리와 스케일 아웃이 가능합니다.

마무리

Climbing Cam 프로젝트에서 발생한 '데이터 크기와 시스템 성능 간의 딜레마'를 Claim Check Pattern을 통해 우아하게 해결할 수 있었습니다. 모든 데이터를 무조건 DB에 넣어서 일관성을 강제하거나, 반대로 모든 것을 S3에 의존하는 극단적인 방법 사이에서, 데이터의 특성에 맞게 저장소를 분리하는 아키텍처적 사고의 중요성을 깨닫게 된 좋은 경험이었습니다.
